## 2. 観点別の採点詳細

### プランセットA

#### A-01: VOICEVOX × Remotion(TTS メタデータ駆動)— 90点

**実現可能性 22/25**
- 「`docker run --rm -p 50021:50021 voicevox/voicevox_engine:cpu-latest`」「`jq '.speedScale=1.05 | .pauseLengthScale=1.1'`」など、実行可能なコマンドレベルまで具体化。VOICEVOX の `/audio_query` → `/synthesis` の2段 API、`POST /user_dict_word` のユーザー辞書 API はいずれも実在し、正確。尺確定の Python コード(`len(wav)/sr*1000` + `np.zeros` で無音挿入)は そのまま動く水準。
- 「MacBook Pro (M1 Pro): 全工程がここで完結する」— VOICEVOX CPU 実行・Remotion レンダとも M1 で現実的。GPU 依存を外した構成判断は環境整合性が高い。
- 減点: 「最初の1本の完成: 実働約3日」は、Day 3 に「タイポグラフィ/キーワードポップ同期/エビデンスA・B・Cバッジ/棒グラフコンポーネント/ぶった斬りコーナー演出を作り込み」を全部詰めており楽観的(B の 5.5〜10人日 と比べ約半分)。また Docker の VOICEVOX イメージは amd64 前提で M1 ではエミュレーション動作になる点は未注記(「アプリ同梱エンジン or Docker」と逃げ道はあるため小減点)。—3。

**音声・映像同期 19/20**
- 「合成後 WAV のサンプル数から実測(`len(wav)/sr`)。予測式に頼らないので誤差ゼロ」— タイムスタンプ取得方法が実測ベースで最も堅牢。同期データ形式(`timeline.json` の `{id,start_ms,end_ms,highlights[]}`)、適用方法(「`<Sequence from durationInFrames>` に ms→frame 換算で流し込み。音声 `<Audio>` と同一クロック共有」)まで3点セットが揃う。
- 尺揺れ問題への回答が構造的: 「**設計上発生しない。** スライド表示秒を人間/LLM が固定せず、常に『音声を作ってから、その実測尺に映像を合わせる』向きだから」。
- 会話の間: 「話者交代のたびに `pause_after_ms`(既定 250〜400ms)を無音として挿入」+ 話者別 `speedScale`。
- フォールバック設計が秀逸: 「モーラ照合に失敗しても、そのシーンは『キーワード先頭一括表示』に自動フォールバック」。
- 減点: キーワードの表層文字列→モーラ列の照合(漢字→カナ変換が必要)の実装難度が一行で流されている。—1。

**人間の関与設計 14/15**
- 3点に絞る根拠が明確: 「LLM は医療クレームを微妙に誇張/改変しうる。…**唯一の必須関門**」(manifest レビュー)、「日本語 TTS 最大の品質欠陥は誤読。文字列一致では検出できず耳が要る」。
- インターフェースも具体的: 「②は『WAV 再生 + 対応 `line` 表示 + 辞書登録ボタン』だけの 30 行程度のローカル HTML」。「**意図的に自動のまま残す**: 尺決定・音声結合・シーン→フレーム割当・エンコード」と過剰手作業の排除も明示。
- 減点: レビュー①の差分確認を支援する仕組み(原文との対応表示など)が C ほど踏み込んでいない。—1。

**技術選定とコスト 14/15**
- 選定理由が要件に直結: VOICEVOX は「**モーラ timing をネイティブ出力=同期の実現手段そのもの**」、却下理由も具体的(「Style-Bert-VITS2/クラウド=声は上だが timing 非公開で ASR 必須」)。コストは「実質 50円未満」+「エンジニア実働 3〜4日」で1本あたり・初期の両方を明示。Remotion の「法人4名以上は要ライセンス」も正確(実際 Company License は従業員4名以上で必要)。
- 減点: 「VOICEVOX…商用可」はキャラごとのクレジット表記義務に触れておらず一面的(C は明記)。—1。

**コンテンツ品質 12/15**
- 尺逆算が定量的: 「日本語 TTS は概ね 6〜7 モーラ/秒 ≒ 300〜360字/分なので、全 `line` の合計を約 1500〜1800 字に収める」。layout の有限集合(`quiz_options` / `bansuzuri` 等)がドラフト構成と対応し、「【エビデンス強度 A】をバッジ化」も押さえている。
- 減点: 軽妙な文体・比喩をどう画面に translate するかの設計が薄く(BGM・ジングルはリスク対策欄に一言)、シーン数・区間配分の設計も B/C より粗い。—3。

**再現性・拡張性 9/10**
- 「すべての可変要素…は `manifest.json` に外出し。Remotion 側は manifest を解釈するだけの汎用レンダラ」「音声バックエンドの差し替え…も `timeline.json` スキーマ互換なので Remotion 側は無改造」。形式揺れは「節の意味で写像 + 欠損 layout スキップ」。Day 4 に「2本目…を無改造で流し」と汎用性検証を工程化している点も良い。—1 は形式揺れ耐性の具体実装(パーサ)が C より浅いため。

#### A-02: Style-Bert-VITS2 × 強制アラインメント — 81点

- **実現可能性 18/25**: Style-Bert-VITS2 の記述は正確(`server_fastapi.py`、`/voice?...&style=Neutral&style_weight=1.0` の API、JP-Extra、JVNV 由来の感情スタイル、VRAM 数 GB — いずれも実在・整合)。ただし (a) WhisperX の日本語アラインは wav2vec2 日本語モデル依存で精度が英語より落ちる既知の弱点に触れていない、(b) コード例の `transcribe_stub` は未定義のまま、`k.startswith(w["word"])` は日本語分かち書きの揺れに脆弱、(c) 「商用利用も可能」はモデルごとの規約確認が必要な主張で無条件には言えない。—7。
- **音声・映像同期 17/20**: 「アラインメントは**シーン内のキーワード位置決めにだけ**使い、シーン尺そのものには介入しない → アライン誤差がスライド切替タイミングに波及しない」という誤差隔離設計は的確。「認識ではないのでハルシネーションが原理的に起きず」も強制アラインメントの説明として正しい。—3 は語境界精度の定量的検証手段がない点。
- **人間の関与 13/15**: 「キーワード highlight のタイミングが発話とズレていないか…数点確認」と追加関与の理由が明確。
- **技術選定とコスト 13/15**: ElevenLabs 経路「概ね数百円〜千円台/本」は料金体系と整合する妥当な幅。「日常量産はプラン01、勝負回のみプラン02」の費用対効果判断も合理的。—2 は SBV2 商用可の断定と、MFA 日本語モデルのセットアップ工数(辞書・G2P)が「+2〜3日」に含まれるか不明瞭な点。
- **コンテンツ品質 11/15**: 「しっとりした導入や感情の起伏…では、より人間に近い抑揚が欲しい回がある」と声の演技を品質要素として設計。差分文書ゆえ映像面の追加はなし。
- **再現性・拡張性 9/10**: 「前段(manifest)と後段(Remotion)はプラン01と**完全共有**」のスキーマ互換設計は高評価。

### プランセットB

#### B-01: 実音声キュー駆動の Remotion パイプライン — 86点

**実現可能性 21/25**
- 全ツール(unified/remark、markdown-it-py、VOICEVOX / AivisSpeech、ffprobe/ffmpeg、Remotion)が実在し、誇張された機能前提がない。「正規表現だけで全文を処理しない。…見出し階層を AST として扱えば再現性が高い」はドラフト実物(`## フック` 等の見出し構成)と正確に整合。
- 工数見積りが3セット中最も誠実: 「エンジニアリング: 4〜7人日…合計: 5.5〜10人日」「初回は 2〜3時間」(レビュー時間)。楽観バイアスが小さい。
- 減点: (a) 音声連結のコマンド「`ffmpeg -f concat -safe 0 -i concat-list.txt -c:a pcm_s16le narration.wav`」には無音(pause)の挿入が含まれておらず、一方 timeline 側は「pause_after_ms を足して絶対時刻に変換する」ため、**このまま実装すると音声と timeline がポーズ分ずれる**。無音 WAV の生成・挿入手順が欠けた実装ギャップ(修正は容易だが同期の核に関わる)。(b) A/C に比べ中間データを生成するコード自体の提示が少ない。—4。

**音声・映像同期 17/20**
- 同期単位の設計思想が明快: 「映像を切り替えたい箇所を cue 境界にする。…これにより、単語単位の複雑なリップシンクや不安定な日本語 forced alignment に依存しなくてよい」— 日本語 forced alignment の不安定さの認識は正しく、割り切りとして合理的。
- 尺揺れ対処が3セット中最も網羅的: 「1. pause_after_ms を安全範囲内で圧縮する。2. scene の余白アニメーションを短縮する。3. LLM に『削除可能 cue』だけを再圧縮させる」に加え、唯一**短すぎる場合**まで扱う(「沈黙を増やすのではなく、フックや実践結論の cue を少し厚くする」)。
- 会話テンポの設計も最も細かい: intent 別 pause 表(「正解発表前 | 500〜650」等)、「話者交代が速すぎると漫才のようになり、遅すぎると教材の密度が落ちる」。
- 減点: (a) 語単位ハイライトは「文字数またはモーラ数の重みで cue 内のおおよその出現位置を計算」という近似で、A/C の実データ由来 timing より精度が劣る(厳密箇所は sub-cue 分割で回避しており破綻はしないが、機構としては一段浅い)。(b) 上記の pause 挿入ギャップは「合成時の適用方法」の穴でもある。—3。

**人間の関与設計 14/15**
- 3レビューとも「対象/見るもの/修正方法/理由」の4点セットで最も運用手順書に近い。「『飲み会』『油は無罪』など、誤解されやすい表現に補足があるか」はドラフト実物のタイトル群に即した具体性。低解像度プレビュー(720p)を人間レビュー専用の中間成果物として工程化した点(「同期は機械的に合っていても、視聴体験として読めるかは実物を見ないと判断できない」)は独自の良さ。
- 減点: レビューを支援するツール面(A の簡易 HTML、C の未登録語自動リストアップに相当するもの)が薄い。—1。

**技術選定とコスト 12/15**
- 代替比較は最も幅広い(「After Effects 手作業 | 不採用 | 1本目は綺麗でも10本への再現性が低い」「Manim | 条件付き」「PowerPoint 自動生成 + 録音合成 | 条件付き」)。「同期方式は TTS エンジンに依存させず、最終的に生成された音声ファイルの duration を測る形に統一する」という選定原則も良い。
- 減点: コストが「数十円〜数百円程度」「おおむね数百円〜千円未満を想定」と幅が広く精度が低い。また「RTX 4090 は…将来のローカル画像生成、Whisper 系の検査に使う」「10本をまとめて出すなら Windows 側に寄せる」と2台の使い分け理由が弱い(本構成なら実質1台で足りることを明言していない)。—3。

**コンテンツ品質 14/15**
- 3セット中最良。区間別の尺・シーン数予算表(「解説の山場 | 12〜16 | 150〜190」)、文字量規律(「1 scene の画面上の主テキストは 28文字以内」「1行は原則 14〜18字」)、そして健康情報の安全策が突出: 「観察研究と RCT を同じ強さに見せない」「『効く』『防げる』は、ドラフトが慎重に書いている場合は『関連』『有望』『余地がある』に戻す」「医療助言の新規追加はしない。ドラフトにない断定を足さない」。クイズ演出も「全選択肢を読み上げすぎない。画面に出し、音声では代表的な迷いどころを拾う」と5分尺への圧縮を具体化。
- 減点: 「楽しく気楽に」側の演出(BGM・ジングル・遊びの演出)が安全側に寄り手薄。—1。

**再現性・拡張性 8/10**
- 「intent と template の対応表を固定し、例外だけ手修正」「未知セクションは補助素材として扱う」と形式揺れ耐性は明確。「手修正は YAML の該当行だけで済ませる」。
- 減点: 声の変更・テンプレ追加・別フォーマット展開など将来拡張の記述がほぼなく、TTS 差し替え時の互換契約(A/C の timeline スキーマ互換に相当)が設計として明文化されていない。—2。

### プランセットC

#### C-01: 決定論的タイムライン方式(VOICEVOX × Remotion)— 92点

**実現可能性 22/25**
- VOICEVOX AudioQuery の仕様理解が最も深い: 「各モーラの `consonant_length` と `vowel_length`(秒)、アクセント句末の `pause_mora`、全体の `prePhonemeLength` / `postPhonemeLength`」— 実在のフィールド名で正確。尺計算式(`/ speedScale` を含む)もエンジンの実挙動と整合する。寛容パーサの正規表現(`【エビデンス強度\s*([A-D])…】`)はドラフト実物の注記形式(`【エビデンス強度 A: 統制された実験、追試あり】`)にそのまま適用可能。
- 環境整合も的確: 「本パイプラインは VRAM 依存でない。…開発・レビュー・レンダはすべて Mac で完結」「RTX 4090 機は任意のアクセラレータ…Qwen2.5-32B-Int4(24GB に収まる)」— Int4 の 32B は概ね 18〜20GB で 24GB に収まり、主張は正しい。工数「約4〜5人日」は A より現実寄り。
- 減点: (a) 「**推定ではなく計算**なので誤差ゼロ」はサンプル丸め・エンジンバージョン差を無視したやや過剰な断定(実用上は正しいが検証工程を Step 3 に明示すべき)。(b) `emphasis` の「文字範囲に対応するモーラ区間」の対応付け(漢字→カナ)の実装が A 同様に一行流し。(c) 口パク・2アバターまで初期スコープに含み、Step 4「1.5日」はやや楽観。—3。

**音声・映像同期 19/20**
- 3点セットが最も体系的。取得方法: 「音声波形を生成する前に、各モーラ…の長さ・無音ポーズ長・前後無音長をすべて秒で返す。…合成前に決定論的に分かる」。形式: `wordTimings`/`emphasis` の絶対秒つき `timeline.json` を実例提示。適用: 「合成時の適用は『フレーム番号の一致』に還元される」。
- 会話特有の間の規則化が最良: 状況別の無音表に「問い→答え…400–500 ms(一拍おく)」「クイズの『考える間』| 2.5–3.5 s(画面は選択肢のまま、BGMだけ)」まで含み、定数を「`pacing.json` に切り出し、プレビュー(レビュー③)で微調整可能」と運用まで接続。
- 尺揺れ: 「合成前に尺確定…±20秒に収まらなければ自動で圧縮/展開を1回リトライ、それでも外れたら人間レビュー①にフラグ」。
- 減点: B が扱った「短すぎる場合」の質的対処(無音でなく内容を厚くする)への言及がない。—1。

**人間の関与設計 14/15**
- 各レビューに「何を見る/なぜここ/どう直す/次工程へ」が揃う。特にレビュー負荷を下げる仕掛けが具体的: 「誤読候補は『辞書未登録語』として自動リストアップし、その分だけ確認」「`【強度X】`タグは原文からの逐語コピーをプロンプトで強制しておき、人間は改変されていないかだけ確認すればよい」。「**自動化を維持する所(手作業にしない)**: 字幕の1個ずつの配置、スライド切替時刻、口パク、レンダ、10本のバッチ実行」と反対側も明示。
- 減点: レビュー①のインターフェースが「JSON/MDを直接編集(または簡易 Web フォーム)」とやや曖昧。—1。

**技術選定とコスト 14/15**
- 「TTS | VOICEVOX…**合成前 mora 長=決定論的同期の生命線**」と選定理由が要件の核に直結。代替の劣後理由も正確(「クラウド Neural…は…尺が事前確定しない→強制アライメント要」)。ライセンス面の目配りが3セット中最良: 「VOICEVOX 音源のライセンス/クレジット義務…規約に従いエンドロールにクレジット」「Remotion は個人/小規模無料、一定規模の企業は要ライセンス(明記)」「Noto Sans JP をバンドル、`<Font>`で明示ロード」。コストは1本 ¥20〜50 + 人間30〜60分、初期4〜5人日と両方明示。
- 減点: ローカル LLM 代替(Qwen)の日本語台本品質の検証手順がなく「やや劣化」の一言。—1。

**コンテンツ品質 14/15**
- 専用の §5 で translate 戦略が最も具体的: 「皮肉(『救急車を廃車にする』等)は講師のセリフとして残し、画面にその比喩を短いイラスト or 大文字で添える」「画面中央に**巨大な強調語1つ**(例:『督促状が来なくなる借金』)+ 下に一行補足」「`【強度A】`=緑…『観察研究(因果は保留)』等のニュアンスを色と短語で伝える」— いずれもドラフト実物の文言を踏まえている。情報量設計も定量的: 「平均12–18秒/シーン、15–22シーン」「全俗説は入れず、最も面白い2つに絞る」「20分想定のフロンティア編は…『約6分』に自動延長し人間に通知」とドラフト間の分量差まで見ている。

## 3. 総合所見

### 各セットの最大の強み・最大の弱点

**プランセットA(90点・2位)**
- **最大の強み**: 実装の即着手可能性。curl/jq/Python/TSX が実コード水準で提示され、「同期は"調整"ではなく"導出"される」という設計原理と、失敗時のグレースフルデグレード(「一括表示へ自動フォールバック」)まで揃う。README の使い分け指針も「同じ manifest から音声バックエンドだけ差し替えて AB 比較」という実験計画まで踏み込み、2案が本当に1システムの2構成として設計されている点は高品質。
- **最大の弱点**: コンテンツ品質設計の相対的な薄さ。ドラフトの軽妙さを画面にどう写すかが layout 名の列挙にとどまり、B の安全規範や C の演出具体案に及ばない。工数「実働約3日」も楽観側。

**プランセットB(86点・3位)**
- **最大の強み**: コンテンツ品質と運用の誠実さ。「観察研究と RCT を同じ強さに見せない」等の健康情報安全規範、区間別シーン予算表、文字量規律、そして3セット中最も現実的な工数見積り(5.5〜10人日)。尺揺れ対処も唯一「短すぎる場合」まで設計。
- **最大の弱点**: 同期機構の詰めの甘さ。timeline には pause_after_ms を加算するのに、提示された ffmpeg concat コマンドには無音挿入がなく、そのままでは音声と timeline がずれる実装ギャップがある(修正容易だが「技術的な核」での穴)。語ハイライトも文字数比の近似止まり。単一プランのため README(使い分け指針)は評価対象外。

**プランセットC(92点・1位)**
- **最大の強み**: 同期の「合成前決定論」を仕様レベル(フィールド名・計算式・100ns単位換算まで)で正確に押さえた技術理解の深さと、コンテンツ品質(「クイズの考える間 2.5–3.5s」「巨大な強調語1つ+一行補足」「強度タグの逐語コピー強制」)・運用資産(横断発音辞書・pacing.json が「回を重ねるほど整い、手間が逓減」)までを1本の設計思想で貫いた総合力。README の使い分け指針も「回ごと・話者ごとに TTS を混在可能」まで示し実用的。
- **最大の弱点**: 断定の強さ。「誤差ゼロ」の過剰主張、C-02 の Azure 単価の事実誤認($4/百万字)。また初期スコープ(口パク・アバター)がやや過積載で、Step 4 の 1.5日は楽観。

### 順位

1. **プランセットC — 92点**(C-01)
2. **プランセットA — 90点**(A-01)
3. **プランセットB — 86点**(B-01)

A と C は「VOICEVOX timing × Remotion × timeline.json 契約」という同型のアーキテクチャに独立に到達しており、実質的な優劣は僅差。C は同期仕様の正確さ・コンテンツ演出・育つ資産の設計で上回り、A は実測ベース(合成後 WAV 実測)の分だけ同期の頑健性とフォールバック設計で上回る。B はアプローチの堅実さと品質規範で独自の価値を持つが、同期の核に実装ギャップを残した。

### 実際に採用するなら

**C-01 を基幹に据え、A-01 の実測検証とフォールバック、B-01 の品質規範を移植するハイブリッドを推奨する。**

1. **基幹パイプライン**: C-01(合成前尺確定 + timeline.json 契約 + 寛容パーサ + 育つ辞書)。ただし「誤差ゼロ」を鵜呑みにせず、**A-01 の「合成後 WAV 実測」を検証ゲートとして併設**する(計算尺と実測尺の差分をチェックし、閾値超なら実測を採用)。これで C の優雅さと A の頑健さを両取りできる。
2. **台本生成プロンプトとレビューチェックリスト**: B-01 の安全規範(「ドラフトにない断定を足さない」「観察研究と RCT を同じ強さに見せない」「効く→関連に戻す」)と区間別シーン予算表・文字量規律をそのまま移植する。健康教材としての事故防止価値が最も高い。
3. **初期スコープ**: 口パク・アバターは C-01 の初期スコープから外し(B の「最初は簡単な2Dアバターでよい」の判断が正しい)、まず sleep-01 → 2本目の無改造適用(A-01 Day 4 の検証工程)を通す。
4. **上位ライン**: 看板回向けには C-02 の Azure WordBoundary 経路を第一候補とする(A-02 の Style-Bert-VITS2 より、タイムスタンプが API ネイティブで得られ工程が短いため)。ただしコストは $16/100万文字前後で再計算し、外部送信の可否を先に確認すること。

現実的な総工数は、A の3日と B の5.5〜10人日の間、**約5〜7人日**で最初の1本+2本目検証まで到達できると見積もる。
