# Plan 01: 実音声キュー駆動の Remotion 動画生成パイプライン

## 0. 設計方針

このプランでは、健康教育ドラフトを「二人会話の台本」と「映像キュー付きタイムライン仕様」に変換し、実際に合成した音声の長さを基準に映像を組み立てる。同期の中心に置くのは、LLM が予測した秒数ではなく、TTS 後に得られる WAV の実測 duration である。

全自動を狙いすぎず、人間は「医学・健康情報としての言い回し」「5分動画としての密度」「TTS 読み間違い」の3点だけを見る。スライド切り替え、字幕、話者交代、間の挿入、MP4 書き出しは機械的に再現できる形にする。

対象ドラフトは、フック、クイズ、正解、解説、ぶった斬り、答え合わせ、今日から使える結論、出典という型を持つ。動画ではこの構造を崩さず、以下のように圧縮する。

- フック: 25〜35秒
- クイズ: 35〜45秒
- 正解と主張: 20秒
- 解説の山場: 150〜190秒
- ぶった斬り/誤解訂正: 45〜60秒
- 今日から使える結論: 35〜45秒
- 出典・注意: 10〜15秒

最終尺は 4分40秒〜5分20秒を許容範囲、目標は 5分00秒前後とする。

## 1. アーキテクチャ概要

```text
education/health/drafts/*.md
  |
  | 1. Markdown 構造解析
  v
draft-structure.json
  - title / field / sections
  - quiz choices / correct answers
  - evidence notes / sources
  - strong phrases
  |
  | 2. 会話台本生成
  v
script-cues.yaml
  - speaker: A or B
  - text
  - intent: hook / quiz / evidence / myth_bust / takeaway
  - visual_hint
  - evidence_level
  - pause_after_ms
  |
  | 3. 人間レビュー 1
  v
approved-script-cues.yaml
  |
  | 4. TTS 合成、読み辞書適用、音声 duration 実測
  v
audio/*.wav + measured-cues.json
  |
  | 5. タイムライン生成
  v
timeline.json
  - cue start/end
  - scene start/end
  - animation timing
  - subtitle spans
  |
  | 6. Remotion 低解像度プレビュー
  v
preview.mp4
  |
  | 7. 人間レビュー 2
  v
final timeline.json
  |
  | 8. Remotion + ffmpeg で本番レンダリング
  v
final.mp4
```

中間成果物はすべて JSON/YAML と WAV にする。1本目で整えたテンプレートを他の9本にも同じ処理で流せるようにし、手修正は YAML の該当行だけで済ませる。

## 2. 各工程の設計

### 2.1 Markdown 構造解析

実装方針は Python または Node.js の Markdown parser で見出し単位に分割する。正規表現だけで全文を処理しない。対象ドラフトは概ね `## フック`、`## クイズ`、`## 正解`、`## 解説`、`## 今日から使える結論`、`## 主要な出典` を持つため、見出し階層を AST として扱えば再現性が高い。

抽出する情報:

- タイトル、分野、想定学習時間
- クイズ本文、選択肢 A〜F、正解
- 太字語句、比喩表現、俗説として斬る対象
- `【エビデンス強度 A/B/C: ...】` の注記
- 主要な出典
- 箇条書きの実践結論

出力例:

```yaml
title: "寝だめはできるか — 睡眠負債の返済計画"
field: "睡眠"
quiz:
  question: "睡眠の「借金」と「貯金」について、正しいものをすべて選んでください。"
  choices:
    A: "平日の睡眠不足は、週末にたっぷり寝れば完全にリセットできる"
    B: "睡眠を6時間に制限され続けた人は..."
  correct: ["B", "C", "D"]
evidence_notes:
  - level: A
    claim: "6時間睡眠群の認知成績は14日間下がり続けた"
    source_hint: "Van Dongen 2003"
takeaways:
  - "「眠気に慣れた」は信用しない"
```

### 2.2 会話形式の音声シナリオ生成

LLM を使って、ドラフトを5分向けの二人会話に圧縮する。ここでは高品質な日本語要約とトーン維持が重要なので、クラウド LLM を第一候補にする。モデルは固定せず、OpenAI / Anthropic / Google のうち日本語の自然さと JSON 出力安定性が高いものを選べる設計にする。

会話の役割:

- 話者 A: 進行役。落ち着いて要点を整理する。
- 話者 B: 視聴者代表。俗説を言う、驚く、ツッコむ、生活場面に戻す。

台本生成時の制約:

- 1 cue は原則 1〜2文、2〜8秒程度。
- 1 scene は 1〜3 cue、8〜14秒程度。
- 1 scene の画面上の主テキストは 28文字以内、補助テキストは 2行まで。
- エビデンス強度は A/B/C バッジとして残す。
- 出典名は動画中では最小限にし、詳細は最後の小さな出典画面へ送る。
- 「飲み会」など誤解を招くキャッチコピーは、必ず安全側の補足 cue を隣接させる。
- 医療助言の新規追加はしない。ドラフトにない断定を足さない。

出力する `script-cues.yaml` の例:

```yaml
- id: c001
  speaker: A
  intent: hook
  text: "平日は6時間、週末は昼まで。これで睡眠の借金は返せると思いますか。"
  visual:
    template: title_question
    headline: "寝だめで返せる?"
    keywords: ["睡眠の借金"]
  pause_after_ms: 180

- id: c002
  speaker: B
  intent: viewer_misconception
  text: "週末にまとめて寝れば、だいたい帳尻が合う気がします。"
  visual:
    template: character_react
    headline: "よくある答え"
    keywords: ["帳尻"]
  pause_after_ms: 260
```

### 2.3 音声合成

第一候補はローカル TTS の VOICEVOX または AivisSpeech 系を Windows 11 Pro マシンで動かす。理由は、日本語音声の扱いやすさ、複数話者の用意、ローカル実行による反復コストの低さ、合成結果を cue 単位で何度も作り直せる点である。RTX 4090 は必須ではないが、GPU 対応エンジンを使う場合の余裕が大きい。

音声設計:

- 話者 A: 明瞭で少し低め、説明に向く声。
- 話者 B: 少し高め、反応とツッコミに向く声。
- 速度は標準よりやや速め。ただし5分に収めるために無理に早口にしない。
- cue 間の基本ポーズは 160〜260ms。
- 話者交代時は 240〜360ms。
- クイズの選択肢後、正解発表前、重要結論前は 450〜650ms。

読み間違い対策として、固有名詞・研究名・外来語・略語を辞書化する。

例:

```yaml
pronunciation_dictionary:
  PREDIMED: "プレディメド"
  Van Dongen: "ヴァン ドンゲン"
  WHO: "ダブリュー エイチ オー"
  社会的時差ボケ: "しゃかいてき じさぼけ"
```

商用品質を優先する場合の代替として、VOICEPEAK、ElevenLabs、日本語対応のクラウド TTS を差し替えられるようにする。ただし同期方式は TTS エンジンに依存させず、最終的に生成された音声ファイルの duration を測る形に統一する。

### 2.4 映像生成

映像は Remotion を第一候補にする。React/TypeScript で宣言的にシーンを組み、JSON の timeline から 1080p/30fps の MP4 を安定して生成できるためである。After Effects の手作業や生成 AI 動画は使わない。今回の要件は「シンプルなアニメーションと大きめの文字」であり、再現性と同期の正確さが重要だからである。

テンプレート例:

- `title_question`: タイトル、問い、二人の小さな立ち絵
- `quiz_choices`: A〜F の選択肢を2列で表示し、読み上げに合わせて点灯
- `answer_reveal`: 正解ラベルを順に表示
- `myth_bust`: 俗説を赤い取り消し線で斬り、正しい見方を出す
- `evidence_card`: 主張、エビデンス強度 A/B/C、研究名を短く表示
- `analogy`: 「睡眠負債」「体重計 KPI」など比喩を簡単な図解にする
- `practical_steps`: 今日から使える結論を3つ表示
- `source_footer`: 主要出典を小さく表示

画面設計のルール:

- 1 scene 1メッセージ。
- 主要文字はスマホ視聴でも読める大きさにする。
- 1行は原則 14〜18字、最大でも 22字程度。
- エビデンス強度は色とラベルで表示するが、煽りにならないよう説明文を添えすぎない。
- 会話の話者に合わせて左下/右下のキャラクターを軽く点灯させる。
- 派手な背景動画ではなく、白〜薄い色面、太い文字、図解、短いモーションを基本にする。

キャラクターは最初は簡単な2Dアバターでよい。生成画像を使う場合も、固定の2人を一度だけ作り、以後は表情差分程度に留める。動画ごとに絵柄が変わるとシリーズとしての信頼感が落ちるためである。

### 2.5 同期・合成

音声は cue 単位の WAV を ffmpeg で連結し、同時に各 cue の開始・終了時刻を `timeline.json` に書き込む。Remotion はこの `timeline.json` を読み、現在フレームがどの cue / scene に属するかを計算して表示を変える。最後に Remotion の映像と連結済み音声を mux して MP4 にする。

代表的な処理コマンド例:

```bash
ffprobe -v error -show_entries format=duration -of json audio/c001.wav
ffmpeg -f concat -safe 0 -i concat-list.txt -c:a pcm_s16le narration.wav
npx remotion render src/Video.tsx output/video-only.mp4 --props=timeline.json
ffmpeg -i output/video-only.mp4 -i narration.wav -c:v copy -c:a aac -shortest final.mp4
```

## 3. 音声と映像の同期方式

同期の核は、以下の4段階である。

### 3.1 cue を同期の最小単位にする

台本生成時点で、映像を切り替えたい箇所を cue 境界にする。たとえば「クイズの A を読む」「B を読む」「正解を出す」「俗説を斬る」「実践結論1を出す」を別 cue にする。これにより、単語単位の複雑なリップシンクや不安定な日本語 forced alignment に依存しなくてよい。

### 3.2 TTS 後に実測 duration を取る

TTS の発話長は予測しない。各 cue の WAV を生成したあと、ffprobe で実測し、pause_after_ms を足して絶対時刻に変換する。

```json
{
  "cueId": "c014",
  "speaker": "B",
  "audio": "audio/c014.wav",
  "startMs": 82340,
  "durationMs": 5120,
  "pauseAfterMs": 300,
  "endMs": 87760,
  "sceneId": "s006"
}
```

### 3.3 scene は cue の束として定義する

scene の開始は最初の cue の startMs、終了は最後の cue の endMs にする。映像側は scene 内の相対時刻でアニメーションする。

```json
{
  "sceneId": "s006",
  "template": "evidence_card",
  "startMs": 78100,
  "endMs": 87760,
  "headline": "慣れたのは感覚だけ",
  "badge": "エビデンス A",
  "cues": ["c013", "c014"]
}
```

Remotion 側では `frame / fps * 1000` を現在時刻に変換し、該当 scene と cue を引く。これでスライド切り替え、話者の点灯、字幕、選択肢のハイライトが音声に追従する。

### 3.4 細かいハイライトは cue 内相対時間で扱う

重要語句の点灯は、完全な単語タイムスタンプではなく cue 内の相対割合でよい。たとえば `keywords` に対して、文字数またはモーラ数の重みで cue 内のおおよその出現位置を計算する。厳密に合わせたい箇所、たとえば「正解は、B・C・Dです」は、最初から `B`、`C`、`D` を別 cue または短い sub-cue に分ける。

この設計は、TTS エンジンごとの音素タイムスタンプ機能に依存しない。音声が差し替わっても再測定すれば timeline が再生成される。

### 3.5 尺の揺れへの対処

TTS 後の合計尺が範囲外になった場合は、自動で次の順に調整する。

1. pause_after_ms を安全範囲内で圧縮する。
2. scene の余白アニメーションを短縮する。
3. LLM に「削除可能 cue」だけを再圧縮させる。
4. それでも 5分20秒を超える場合は人間レビューで削る。

逆に短すぎる場合は、沈黙を増やすのではなく、フックや実践結論の cue を少し厚くする。教育動画としての理解時間を守るためである。

### 3.6 二人会話の間とテンポ

二人会話では、話者交代が速すぎると漫才のようになり、遅すぎると教材の密度が落ちる。そこで pause は intent ごとに持つ。

| cue 種別 | pause_after_ms の目安 |
|---|---:|
| 同一話者の説明継続 | 120〜200 |
| 話者交代 | 240〜360 |
| ツッコミの後 | 180〜280 |
| クイズ選択肢間 | 180〜260 |
| 正解発表前 | 500〜650 |
| 重要結論後 | 400〜600 |

話者交代の pause は timeline 生成時に自動加算する。台本 YAML に個別指定があればそちらを優先する。

## 4. 人間の関与ポイント

### 4.1 台本レビュー

対象: `script-cues.yaml`

見るもの:

- ドラフトの主張が歪んでいないか
- エビデンス強度 A/B/C が落ちていないか
- 「飲み会」「油は無罪」など、誤解されやすい表現に補足があるか
- 5分で伝えるべき山場が1〜2個に絞れているか
- 二人会話が軽いが、医療情報としてふざけすぎていないか

理由: 健康情報の正確性とトーンは自動判定しにくい。ここは人間が見る価値が高い。

### 4.2 読み・声レビュー

対象: TTS の短い試聴 MP3 または WAV

見るもの:

- 固有名詞、研究名、英語略語の読み
- 話者 A/B の声質差
- 早口すぎないか
- ツッコミが不自然に強すぎないか

修正方法:

- pronunciation_dictionary を編集
- cue ごとの speed / pitch / pause_after_ms を調整
- 必要なら cue を分割

理由: 日本語 TTS は固有名詞で破綻しやすく、ここを直すだけで完成度が大きく上がる。

### 4.3 低解像度プレビュー

対象: 720p の `preview.mp4`

見るもの:

- 文字が多すぎないか
- クイズ選択肢が読み切れるか
- スライド切り替えが音声より先走っていないか
- エビデンス表示が小さすぎないか
- 5分動画として飽きる区間がないか

修正方法:

- scene template の差し替え
- headline の短縮
- cue の削除または統合
- 重要語句の keywords 調整

理由: 同期は機械的に合っていても、視聴体験として読めるかは実物を見ないと判断できない。

## 5. 技術選定の理由とコスト概算

### 5.1 主な技術

| 領域 | 第一候補 | 理由 |
|---|---|---|
| 構造解析 | Node.js unified/remark または Python markdown-it-py | Markdown AST を扱える。ドラフト形式の揺れに強い |
| 台本生成 | クラウド LLM | 日本語の要約、会話化、制約付き YAML 生成の品質が高い |
| TTS | VOICEVOX / AivisSpeech 系ローカル TTS | 日本語、複数話者、低コスト、反復生成しやすい |
| 音声処理 | ffmpeg / ffprobe | duration 実測、連結、mux が安定 |
| 映像生成 | Remotion | JSON timeline から同期動画をコードで再現しやすい |
| プレビュー | Remotion low-res render | 人間レビュー用に高速生成できる |
| 最終出力 | MP4 H.264 + AAC | 汎用性が高い |

Windows 11 Pro + RTX 4090 は、TTS や将来のローカル画像生成、Whisper 系の検査に使う。MacBook Pro は、台本レビュー、Remotion 開発、軽いプレビュー、最終確認に使う。Remotion の本番レンダリングはどちらでもよいが、10本をまとめて出すなら Windows 側に寄せる。

### 5.2 代替案との比較

| 案 | 採否 | 理由 |
|---|---|---|
| After Effects 手作業 | 不採用 | 1本目は綺麗でも10本への再現性が低い |
| 生成 AI 動画を scene ごとに作る | 不採用 | 文字・図解・同期の制御が弱く、健康教材には過剰 |
| Manim | 条件付き | 図解中心なら強いが、会話字幕とテンプレ量産は Remotion のほうが楽 |
| PowerPoint 自動生成 + 録音合成 | 条件付き | 初期実装は早いが、細かいタイムライン制御が弱い |
| クラウド TTS 全振り | 条件付き | 声質は良い可能性があるが、10本で試行錯誤するとコストと利用規約確認が増える |

### 5.3 コスト概算

価格はサービス改定で変わるため、ここでは設計上の概算として見る。

初期構築:

- エンジニアリング: 4〜7人日
- デザインテンプレート作成: 1〜2人日
- TTS 声選定・辞書整備: 0.5〜1人日
- 合計: 5.5〜10人日

動画1本あたり:

- LLM 台本生成: 数十円〜数百円程度。高性能モデルで複数回リトライしても、おおむね数百円〜千円未満を想定。
- ローカル TTS: 電気代レベル。商用 TTS に差し替える場合は、文字数課金で数十円〜数百円程度を想定。
- レンダリング: ローカル計算資源のみ。
- 人間レビュー: 30〜60分。初回は 2〜3時間。

10本制作時の見積り:

- 初期構築後、1本あたりの機械処理は 15〜40分程度。
- 人間レビュー込みで 1本 1〜2時間。
- 初回だけはテンプレ・辞書・密度調整のため 1〜2日かかる。

## 6. コンテンツ品質への配慮

### 6.1 ドラフトの持ち味を動画に変換する

ドラフトの強みは、軽い比喩で入り、クイズで能動的に考えさせ、俗説を斬り、最後に実践へ落とす構成にある。動画でもこの流れを保つ。

- フックは必ず生活場面から入る。
- B話者に「よくある誤解」を言わせ、A話者が訂正する。
- クイズは全選択肢を読み上げすぎない。画面に出し、音声では代表的な迷いどころを拾う。
- 解説はエビデンス A の主張を中心に置き、B/C は補助として扱う。
- ぶった斬りコーナーは短く、1〜2個に絞る。
- 最後は「今日から使える結論」3つで終える。

### 6.2 5分・数十ページの情報量設計

1 scene あたり平均 10秒、全体で 26〜34 scene を想定する。これで「数十ページを切り替える」感覚を出しつつ、視聴者が読める速度を保つ。

目安:

| 区間 | scene 数 | 秒数 |
|---|---:|---:|
| タイトル/フック | 3〜4 | 25〜35 |
| クイズ | 4〜5 | 35〜45 |
| 正解 | 2 | 15〜25 |
| 解説の山場 | 12〜16 | 150〜190 |
| 俗説訂正 | 4〜6 | 45〜60 |
| 実践結論 | 3〜4 | 35〜45 |
| 出典 | 1 | 10〜15 |

### 6.3 健康情報としての安全策

- ドラフトにある主張以上の医療助言を足さない。
- エビデンス強度を画面から消さない。
- 観察研究と RCT を同じ強さに見せない。
- 「効く」「防げる」は、ドラフトが慎重に書いている場合は「関連」「有望」「余地がある」に戻す。
- 個別疾患の治療判断に見える表現は避ける。

## 7. リスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| 尺が5分を超える | 元ドラフトは12〜15分想定なので圧縮が必要 | cue 数と文字数に上限を置く。TTS 後に duration gate で再圧縮 |
| 健康情報の歪み | 会話化で断定が強くなる | 台本レビューでエビデンス注記と原文対応を確認 |
| TTS の読み間違い | 研究名、英語、専門語で起きる | 読み辞書、cue 分割、試聴レビュー |
| 同期ズレ | TTS 長の予測が外れる | 予測せず、WAV 実測 duration から timeline を生成 |
| 文字過多 | Markdown の情報を詰め込みすぎる | 1 scene 1メッセージ、文字数バリデーション |
| 会話が軽すぎる | 健康教材として信頼感が下がる | A は落ち着いた説明、B は視聴者代表に限定 |
| ドラフト形式の揺れ | コラムや表が入る回がある | AST 解析 + セクション分類。未知セクションは補助素材として扱う |
| TTS ライセンス | 声の商用利用条件が異なる | 採用前に利用規約を確認し、声 ID とライセンスを記録 |
| 10本で品質が揺れる | テンプレ選択が毎回変わる | intent と template の対応表を固定し、例外だけ手修正 |

## 8. 実装ロードマップ

### Day 1: 最小パイプライン

- Markdown から構造 JSON を作る。
- 1本のドラフトで title、quiz、correct、evidence、takeaways を抽出する。
- LLM に `script-cues.yaml` を出させるプロンプトを作る。
- cue 文字数、scene 数、想定尺のバリデーションを作る。

成果物: `draft-structure.json`、`script-cues.yaml`

### Day 2: TTS と timeline

- 話者 A/B の声を選ぶ。
- cue ごとに WAV を生成する。
- ffprobe で duration を測る。
- pause を足して `timeline.json` を生成する。
- 音声を連結して `narration.wav` を作る。

成果物: `audio/*.wav`、`narration.wav`、`timeline.json`

### Day 3: Remotion テンプレート

- title、quiz、answer、evidence、myth_bust、takeaway の6テンプレートを作る。
- timeline から scene を表示する。
- cue に合わせて字幕と話者点灯を切り替える。
- 720p preview を出す。

成果物: `preview.mp4`

### Day 4: 初回レビューと修正

- 台本レビューで主張の歪みを直す。
- 読み辞書を整える。
- 文字量が多い scene を削る。
- 尺が 4分40秒〜5分20秒に入るよう再生成する。

成果物: `approved-script-cues.yaml`、修正版 `timeline.json`

### Day 5: 本番レンダリング

- 1080p/30fps で本番レンダリングする。
- 音声を AAC にして mux する。
- 冒頭、クイズ、正解、結論、末尾を重点チェックする。
- 同じパイプラインで2本目のドラフトを流し、汎用性を確認する。

成果物: `final.mp4`、2本目の `preview.mp4`

## 9. 最初の1本に選ぶ題材

最初の検証題材は `sleep-01-nedame.md` がよい。理由は、睡眠負債という比喩が映像化しやすく、クイズ、実験、俗説訂正、実践結論のバランスが良いからである。

最初の動画で検証するポイント:

- 「睡眠の借金」という比喩を 5分で理解できるか
- Van Dongen 2003 のエビデンス A を短く正確に出せるか
- クイズ B/C/D の正解発表が気持ちよく同期するか
- 「週末寝だめは悪」ではなく「平日の設定が問題」と誤解なく伝わるか

この1本が通れば、運動、油、認知症予防のような他テーマにも同じテンプレートを適用できる。
