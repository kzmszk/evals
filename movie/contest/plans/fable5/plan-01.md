# 設計プラン 01: 決定論的タイムライン方式(VOICEVOX × Remotion)

> **一行サマリー**: 音声の尺を「合成する前に」秒単位で確定できる VOICEVOX の mora 長データを唯一の真実(single source of truth)にし、そこから音声・字幕・アニメーションを一括生成する。同期がズレる余地を構造的に消すのが本プランの核。

---

## 0. 設計思想 — なぜこの構成か

動画生成で最も壊れやすいのは「音声を作ってみたら思ったより長かった/短かった」問題(尺の揺れ)である。多くのパイプラインは **音声を合成 → 後から Whisper 等で書き起こして時刻を推定 → 映像に貼る** という順で組むため、推定誤差・累積ドリフト・話者交代の間の乱れが必ず残る。

本プランはこれを逆転させる。**VOICEVOX の `/audio_query` は、音声波形を生成する前に、各モーラ(子音+母音)の長さ・無音ポーズ長・前後無音長をすべて秒で返す。** つまり「この発話の WAV は何秒になるか」「◯文字目は発話開始から何秒後に鳴るか」が合成前に決定論的に分かる。この timing をそのまま映像側の唯一の真実として使えば、音声・字幕ハイライト・アニメーション・口パクが**同一データ源から導出**され、原理的にドリフトしない。

これがプラン全体を貫く一本の背骨である。

## 1. アーキテクチャ概要

```
 draft.md (health教材, 80-120行)
      │
      │ ① 構造パース(見出し=フック/クイズ/正解/解説/まとめ を検出)
      ▼
 draft.json (正規化された節データ)
      │
      │ ② シナリオ生成(Claude API / 構造化出力)
      ▼
 script.json ──────────►【人間レビュー①: 事実・トーン・尺】必須
   (2話者の会話台本 / シーン割り / 強調語 / エビデンス強度タグ)
      │
      │ ③ 発音辞書適用 → VOICEVOX /audio_query(合成前)
      ▼
 audio_query[] ────────►【人間レビュー②: 読み・アクセント】軽量・スポット
   (mora長・pause長を含む。ここで発話尺が確定)
      │
      ├──④a /synthesis → utterance_XX.wav(話者ごとの音声)
      │
      └──④b 尺・mora長から timeline.json を計算(字幕/強調/口パク/シーン切替の時刻)
      │
      │ ⑤ WAV 連結(話者交代の「間」を規則で挿入)→ narration.wav
      ▼
 timeline.json + narration.wav + assets(フォント/アバターSVG/トークン)
      │
      │ ⑥ Remotion(React)が timeline.json を frame に変換して合成
      ▼
      │ ⑦ Remotion Studio でプレビュー ►【人間レビュー③: 見た目・テンポ】軽量
      ▼
 output.mp4(約5分, 1920x1080, H.264 + AAC)
```

データの流れは一方向で、各中間成果物(`draft.json` / `script.json` / `audio_query[]` / `timeline.json`)はすべてファイルとして残る。どの工程でも途中から再実行でき、10本のドラフトへの横展開と差分デバッグが容易。

## 2. 各工程の設計

### ① 構造パース(自動)

Markdown を見出し(`## フック` `## クイズ` `## 正解` `## 解説` `### 小見出し` `## 今日から使える結論` 等)で分割し、正規化 JSON にする。ドラフトによって章立て・分量が違う(12分想定〜20分想定、`### ぶった斬りコーナー` の有無など)ため、**既知の見出しは意味ラベルに、未知の見出しは `section` として素通し**する寛容なパーサにする。`【エビデンス強度 X: ...】` は正規表現で抽出し構造化(後工程でテロップ化するため)。

```python
# 抜粋: 見出しベースの寛容パーサ
SEMANTIC = {"フック":"hook","クイズ":"quiz","正解":"answer",
            "解説":"explain","今日から使える結論":"takeaway","選択肢の答え合わせ":"answerkey"}
# 【エビデンス強度 A: ...】→ {level:"A", note:"..."}
EVID = re.compile(r"【エビデンス強度\s*([A-D])[:：]?\s*([^】]*)】")
```

### ② シナリオ生成(自動 + プロンプト制約)

`draft.json` を Claude API(構造化出力 / JSON schema 指定)に渡し、**二人の会話台本**を生成する。話者は固定の2ペルソナ:

- **講師(ナビ)**: 要点を締める・俗説をぶった斬る役。落ち着いたトーン。
- **生徒(リスナー代表)**: 素朴な疑問・「え、そうなの?」の合いの手・クイズを声に出して迷う役。

ドラフト構造 → 会話構造への translate ルールをプロンプトに明記:

| ドラフトの節 | 会話・映像への変換 |
|---|---|
| フック | 掛け合いのコールドオープン。生徒が「あるある」を言い、講師が「それ、今日ぶった斬ります」 |
| クイズ | 生徒が選択肢を読み上げ迷う。**画面に選択肢A-Fを大きく表示**し視聴者に問いかけ、数秒の「考える間」 |
| 正解 | 講師が正解を宣言。○×アニメ |
| 解説 | 交互の掛け合い。**重要ワードは強調語としてマーク**(画面で巨大表示)。`【強度X】` は講師が一言触れ、画面にバッジ表示 |
| まとめ | 「今日から使える結論」を箇条書きで大きく。生徒が復唱 |

**尺のガード**: 日本語の自然な会話は概ね 300〜380 文字/分。5分なら台本合計 **1500〜1900文字・15〜22シーン**を予算としてプロンプトに与える。生成後に工程③で実測尺を計算し、±20秒に収まらなければ自動で圧縮/展開を1回リトライ、それでも外れたら人間レビュー①にフラグ。

台本 JSON スキーマ(抜粋):

```json
{
  "meta": {"title": "寝だめはできるか", "accentColor": "#4C9AFF", "targetSec": 300},
  "scenes": [
    {
      "id": "quiz",
      "type": "quiz",
      "onScreen": {"question": "睡眠の借金と貯金、正しいのは?", "options": ["A ...","B ...","..."]},
      "utterances": [
        {"speaker": "student", "text": "えー、全部それっぽく見えるんですけど…", "emphasis": []},
        {"speaker": "teacher", "text": "ここで一回、止めて考えてみましょう。", "emphasis": ["止めて"]}
      ]
    }
  ]
}
```

### ③ 発音辞書適用 → audio_query(合成前・尺確定)

各 utterance の text を、話者に対応する VOICEVOX style_id で `/audio_query` に投げる。健康教材は専門語が多い(`インスリン感受性`, `山中因子`, `並体結合`, `二重標識水法`)。VOICEVOX の誤読・アクセント崩れを防ぐため、**ドラフト横断で再利用するユーザ辞書 (`pronunciation.json`)** を持ち、事前登録した読みを AudioQuery の `kana` に反映させる。

```bash
# audio_query(合成前に mora 長が返る)
curl -s -X POST "http://localhost:50021/audio_query?text=<UTF8>&speaker=3" > q.json
# 尺は合成前に確定できる(下記の式)
```

**この時点で発話尺が秒単位で確定する**(次節の式)。尺の揺れ問題はここで消える。

### ④a 音声合成

確定した AudioQuery を `/synthesis` に渡し、utterance ごとの WAV を書き出す。話者ごとに `speedScale`(講師 1.0 / 生徒 1.05 で軽やかさを演出)、`intonationScale`、`pauseLength` を変えてキャラの話し分けをつける。

```bash
curl -s -X POST "http://localhost:50021/synthesis?speaker=3" \
     -H "Content-Type: application/json" -d @q.json > utterance_007.wav
```

### ④b timeline.json の計算(同期データの生成)

AudioQuery から発話尺と語内タイミングを計算し、`timeline.json` を組み立てる。ここが**同期データのフォーマット**であり、Remotion が読む唯一の入力。

### ⑤ WAV 連結と「間」の挿入

utterance WAV を、話者交代規則に従った無音を挟んで連結し `narration.wav` を作る(規則は §3)。同時に各 utterance の絶対開始秒が確定し、timeline に書き戻す。

### ⑥ 映像合成(Remotion / React)

Remotion は「React コンポーネント=シーン、フレーム番号=時刻」で動画を定義し、ffmpeg 経由で MP4 を書き出すコード駆動の動画フレームワーク。`timeline.json` を読み、`sec → frame = round(sec * fps)`(fps=30)で各シーンを `<Sequence>` として配置、`<Audio>` を該当フレームに置き、テキスト/アニメを同じ timing で駆動する。全レイアウトがコードなので10本で見た目が完全に揃い、Git 管理でき、バッチレンダに向く。

シーン型ごとのコンポーネント(§5 で詳述): `TitleCard` / `HookScene` / `QuizCard` / `AnswerReveal` / `ExplainScene` / `TakeawayList` / `Outro`、加えて画面下の2アバター(話者ハイライト+口パク)。

### ⑦ レンダリング

```bash
npx remotion render src/index.ts HealthVideo out/sleep-01.mp4 \
    --props=./build/sleep-01/timeline.json --concurrency=8
```

## 3. 音声・映像同期の設計(本システムの核)

### 3.1 タイムスタンプの取得方法 — 「合成前決定論」

VOICEVOX の AudioQuery は各モーラの `consonant_length` と `vowel_length`(秒)、アクセント句末の `pause_mora`、全体の `prePhonemeLength` / `postPhonemeLength` / `pauseLength` を持つ。1発話の尺は次式で**合成前に**求まる(VOICEVOX は phoneme 長を `speedScale` で割ってレンダするため、同じ係数で割る):

```
utterance_sec =
   ( prePhonemeLength
   + Σ_moras ( (consonant_length or 0) + vowel_length )
   + Σ_accent_phrases ( pause_mora.vowel_length or 0 )
   + postPhonemeLength ) / speedScale
```

実際に `/synthesis` が返す WAV のサンプル数はこの式と一致する(同じエンジン内部値から生成されるため)。**推定ではなく計算**なので誤差ゼロ。これが Whisper 後付け書き起こし方式に対する決定的優位。

さらに、モーラを先頭から累積すれば「発話開始から t 秒後に、どの文字が鳴っているか」が分かる。強調語(`emphasis`)の文字範囲に対応するモーラ区間の開始・終了秒を引けば、**カラオケ式の語ハイライト**と**口パク(母音区間で口を開く)**が同じデータから出せる。

### 3.2 同期データの形式 (`timeline.json`)

```json
{
  "fps": 30,
  "totalSec": 298.4,
  "audio": "narration.wav",
  "scenes": [
    {"id":"quiz","type":"quiz","startSec":41.2,"endSec":63.8,
     "onScreen":{"question":"…","options":["A …","B …"]},
     "utterances":[
       {"speaker":"student","startSec":41.2,"endSec":45.0,
        "wordTimings":[{"text":"全部","startSec":41.5,"endSec":41.9}]},
       {"speaker":"teacher","startSec":45.3,"endSec":48.1,
        "emphasis":[{"text":"止めて","startSec":46.0,"endSec":46.5}]}
     ]}
  ]
}
```

- `startSec/endSec` は §3.1 の計算 + §3.3 の「間」から積み上げた**絶対秒**。
- `wordTimings/emphasis` はモーラ累積から算出した語内タイミング。
- Remotion 側はこれを全部 `round(sec*fps)` でフレームに変換して使うだけ。合成時の適用は「フレーム番号の一致」に還元される。

### 3.3 話者交代の「間」とテンポ(会話形式特有)

無音を規則化して timeline に反映する:

| 状況 | 挿入無音 |
|---|---|
| 同一話者の文継続 | 120–180 ms |
| 話者交代(通常) | 250–350 ms |
| 問い→答え(生徒の疑問→講師の回答) | 400–500 ms(一拍おく) |
| シーン境界(話題転換) | 600–800 ms |
| クイズの「考える間」 | 2.5–3.5 s(画面は選択肢のまま、BGMだけ) |

これらは定数ファイル `pacing.json` に切り出し、プレビュー(レビュー③)で微調整可能にする。話者ごとの `speedScale`/`intonationScale` 差と併せ、掛け合いのリズムを作る。

### 3.4 尺の揺れへの耐性(まとめ)

- **合成前に尺確定**なので、映像を尺に合わせるのではなく尺を先に知って映像を組む。
- 5分ガードは工程②で実測尺により自動チェック → 超過なら台本圧縮を自動リトライ。
- 万一クラウド TTS に差し替える場合(プラン02)でも、同じ `timeline.json` 形式に、TTS の word-boundary イベントか WhisperX `--dtw` の強制アライメント結果を流し込めば後段は無改変で動く(疎結合設計)。

## 4. 人間の関与ポイント

品質リスクが高く自動化が難しい所にだけ人間を置き、それ以外(時刻計算・レイアウト・レンダ)は完全自動化する。

### レビュー① 台本の事実・トーン・尺 【必須・重い】
- **何を見る**: `script.json` を Markdown プレビューで。会話が原ドラフトの事実とエビデンス強度を歪めていないか、俗説の否定が逆に肯定にすり替わっていないか、軽妙な文体が保たれているか。
- **なぜここ**: 健康情報は誤りが害になる。LLM は強度Aの断定と強度Cの示唆を混ぜたり、皮肉を素で受けたりする。**ここが唯一にして最大の品質ゲート**。
- **どう直す**: JSON/MDを直接編集(または簡易 Web フォーム)。`【強度X】`タグは原文からの逐語コピーをプロンプトで強制しておき、人間は改変されていないかだけ確認すればよい。
- **次工程へ**: 承認で ③ 起動。

### レビュー② 読み・アクセント 【軽量・スポット】
- **何を見る**: 専門語の AudioQuery の `kana`。誤読候補は「辞書未登録語」として自動リストアップし、その分だけ確認。
- **なぜここ**: 誤読は自動検出しづらく、耳で一発。ただし辞書 (`pronunciation.json`) に一度直せば10本で再利用でき、回を追うごとに手間が減る。
- **どう直す**: VOICEVOX GUI でスポット試聴 or 辞書へ読み追加。

### レビュー③ 見た目・テンポ 【軽量】
- **何を見る**: Remotion Studio のライブプレビュー(ホットリロード)。文字の被り、選択肢の可読性、間の気持ちよさ。
- **どう直す**: `pacing.json` の定数、`emphasis` 語の増減。コンポーネントは触らない。

**自動化を維持する所(手作業にしない)**: 字幕の1個ずつの配置、スライド切替時刻、口パク、レンダ、10本のバッチ実行。これらは timeline から機械的に決まるので人手を入れない。

## 5. コンテンツ品質の設計(出力動画の質)

ドラフトの持ち味を映像へ translate する具体策:

- **軽妙な文体を殺さない**: TTS の丸い読みでキツさが出ないよう、生徒役の合いの手・ツッコミで会話のテンポを作る。皮肉(「救急車を廃車にする」等)は講師のセリフとして残し、画面にその比喩を短いイラスト or 大文字で添える。
- **「大きめの文字で重要ワード」**: `ExplainScene` は画面中央に**巨大な強調語1つ**(例:「督促状が来なくなる借金」)+ 下に一行補足、という構成を基本形に。カラオケ式ハイライトで、いま喋っている語が光る。
- **クイズ構成を体験化**: 選択肢A-Fをカード表示し、生徒が声で迷い、2.5–3.5秒の「考える間」で視聴者も考え、○×アニメで答え合わせ。教材の双方向性を動画に持ち込む。
- **エビデンス強度を可視化**: `【強度A】`=緑、`【強度B】`=黄、`【強度C/D】`=グレーのバッジをテロップ表示。「実験ベース」「観察研究(因果は保留)」等のニュアンスを色と短語で伝える。教材の知的誠実さは映像化しても落とさない。
- **情報量設計(5分・数十シーンから逆算)**: 1シーン=1メッセージ。平均12–18秒/シーン、15–22シーン。原ドラフトの`### ぶった斬りコーナー`は「俗説クイックコーナー」として1–2シーンに凝縮(全俗説は入れず、最も面白い2つに絞る)。20分想定のフロンティア編は圧縮率を上げ、必要なら「約6分」に自動延長し人間に通知。
- **統一トーン**: ダークテーマ(リポジトリ慣習に整合)、Noto Sans JP、トピックごとにアクセント色1つ(`meta.accentColor`)。10本でブランドが揃う。

## 6. 技術選定の理由・コスト・トレードオフ

| 工程 | 採用 | 理由(要件との紐付け) | 代替とトレードオフ |
|---|---|---|---|
| シナリオ | **Claude API**(構造化出力) | 日本語の機微・皮肉の保持・JSON 遵守が強い。コスト極小 | ローカル LLM(Qwen2.5-32B on 4090)なら marginal ¥0 だが日本語の機微はやや劣化。→ プロンプト資産は共通化 |
| TTS | **VOICEVOX**(ローカル) | **合成前 mora 長=決定論的同期の生命線**。無料・完全ローカル・複数キャラで2話者を native に実現・日本語特化 | クラウド Neural(Azure/ElevenLabs)は自然さ上・感情豊かだが従量課金&尺が事前確定しない→強制アライメント要。自然さ最優先ならプラン02 |
| 映像 | **Remotion**(React) | フレーム完全同期・コード駆動で10本の見た目統一・Git 管理・バッチ向き・MP4 出力 | MoviePy/ffmpeg 直は自由だがアニメ表現とプレビューが弱い。AE は手作業で再現性が落ちる。※Remotion は個人/小規模無料、一定規模の企業は要ライセンス(明記) |
| アライメント | 不要(VOICEVOX 経路) | 同期は計算で得るため forced alignment 不要 | クラウド TTS 時のみ WhisperX/whisper.cpp `--dtw` を挿す |

### 実行環境の使い分け
- **MacBook Pro (M1 Pro/32GB) を主**: 本パイプラインは VRAM 依存でない。VOICEVOX は CPU で十分実用速度、Remotion レンダも M1 で回る。開発・レビュー・レンダはすべて Mac で完結。
- **RTX 4090 機は任意のアクセラレータ/ローカルLLMホスト**: (a) 台本生成を機密・無料化したい時に Qwen2.5-32B-Int4(24GB に収まる)をローカル実行、(b) VOICEVOX GPU 版で大量バッチを高速化、(c) 将来、背景ビジュアルを SDXL でローカル生成する拡張。**必須ではなく、無い環境でも動く**のが可搬性の担保。

### コスト概算
- **初期構築**: エンジニア実働 **約4〜5人日**(§7)。金銭は実質¥0(全ツール無料/既存機材)。
- **動画1本あたり**:
  - LLM: 台本生成 ~¥20〜50(ローカルLLMなら¥0)
  - TTS: ¥0(VOICEVOX ローカル)
  - レンダ計算: ¥0(自機)
  - **人間時間: 30〜60分**(大半はレビュー①台本確認。②③は各5〜10分。回を重ね辞書が育つと短縮)
  - 実質、金銭コストはほぼゼロ・律速は人間の台本確認時間。

## 7. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| LLM が事実/強度を歪める・皮肉を素で受ける | 健康被害・信頼失墜 | レビュー①必須。`【強度X】`は逐語コピー強制、原文引用を script に併記して差分可視化 |
| VOICEVOX 専門語の誤読・アクセント崩れ | 品質低下 | 横断 `pronunciation.json` 辞書 + 未登録語の自動リストで②を最小化 |
| 合成音声の単調さ(掛け合いが機械的) | 「楽しく気楽に」を損なう | 話者別 speed/intonation、間の規則(§3.3)、文長のリズム。それでも不足なら該当回だけプラン02(クラウド声)へ差し替え可 |
| 尺が5分から外れる | 冗長/駆け足 | 合成前尺で自動チェック→台本自動圧縮リトライ→不可なら人間通知。20分想定編は6分許容 |
| VOICEVOX 音源のライセンス/クレジット義務 | 公開時の規約違反 | 商用可キャラを選定、規約に従いエンドロールにクレジット。辞書化して全回一貫 |
| Remotion の日本語フォント埋め込み漏れ・企業ライセンス | 文字化け/規約 | Noto Sans JP をバンドル、`<Font>`で明示ロード。利用規模に応じライセンス確認 |
| ドラフト形式の揺れ(章立て・分量差) | パース失敗 | 寛容パーサ(既知見出し→意味ラベル、未知→素通し)+ シーン予算の動的調整 |
| レンダ時間 | 運用負荷 | `--concurrency` 調整、変更シーンのみ再レンダ、夜間バッチ |

## 9. 再現性・拡張性

- **1本目専用ハードコードなし**: ドラフト固有情報はすべて `draft.md`→`script.json`→`timeline.json` のデータ側に載り、コード(パーサ/テンプレ/計算)は全10本共通。新ドラフトは「ファイルを差し替えて `render` する」だけ。
- **形式揺れ耐性**: 寛容パーサ + シーン予算の動的調整で、12分想定〜20分想定・`ぶった斬りコーナー`有無を吸収。
- **育つ資産**: `pronunciation.json`(読み辞書)、`pacing.json`(間)、デザイントークン、プロンプトは回を重ねるほど整い、手間が逓減。
- **拡張の容易さ**: 声の変更=VOICEVOX の style_id 差し替えのみ。テンプレ追加=新しいシーン型コンポーネントを1つ足すだけ。クラウド声への切替=TTS モジュールを差すだけ(後段は `timeline.json` 契約で不変=プラン02)。将来の多言語化も、パーサ以降の疎結合構造で段階導入できる。
