# 最終設計: 健康教育動画 生成システム(ハイブリッド構成)

設計コンテスト([contest/results.md](contest/results.md))の評価者提言に基づく採用版。基幹は fable5 plan-01(決定論的タイムライン方式)とし、opus4.8 plan-01 の実測検証ゲート、gpt5.5 plan-01 の安全規範・情報量設計を移植した。各要素の出自は末尾 §13 のマッピング表を参照。

> **一行サマリー**: VOICEVOX の `/audio_query` が合成前に返すモーラ長から音声の尺とタイミングを**計算**し、それを唯一の真実として音声・字幕・シーン切替を導出する。ただし計算値は盲信せず、合成後 WAV の**実測**と突き合わせる検証ゲートを常設する。

---

## 1. 設計原則

1. **音声先行・映像追従**: スライドの表示秒数を人間や LLM が決めることはない。音声の尺が先に確定し、映像はそれに機械的に合わせる。「同期は調整ではなく導出される」
2. **計算と実測の二重化**: 尺とタイミングの一次ソースは AudioQuery からの計算値。ただし全 utterance について合成後 WAV の実測尺(サンプル数 / サンプリングレート)と照合し、差分が閾値(±50ms)を超えたら実測値を採用して警告を出す。「誤差ゼロ」を前提にしない
3. **中間成果物は全てファイル**: `draft.json` → `script.json` → `audio_query[]` → `timeline.json` → `mp4`。一方向の流れで、どの工程からでも再実行できる。git 管理・差分デバッグ・10本横展開の土台
4. **ドラフトにない断定を足さない**: 健康教材として、LLM による主張の増幅を構造的に防ぐ(§5 の安全規範)
5. **初期スコープを絞る**: 口パク・リッチアバターは初期スコープ外。話者表示は「名前ラベル+簡易アイコンの点灯」まで。まず sleep-01 → 2本目の無改造適用を通すことを優先する

## 2. アーキテクチャ

```
 draft.md (education/health/drafts/, 80-120行)
      │ ① 構造パース(寛容パーサ: 既知見出し→意味ラベル、未知→素通し)
      ▼
 draft.json
      │ ② シナリオ生成(Claude Code ヘッドレス + 検証リトライ + 安全規範 + シーン予算)
      ▼
 script.json ─────────►【人間レビュー①: 事実・強度・トーン・尺】必須
      │ ③ 発音辞書適用 → VOICEVOX /audio_query(合成前に尺・モーラ時刻が確定)
      ▼
 audio_query[] ───────►【人間レビュー②: 読み・アクセント】軽量・スポット
      │ ④a /synthesis → utterance_XX.wav
      │ ④b ★検証ゲート: 計算尺 vs WAV実測尺を照合(±50ms 超なら実測採用+警告)
      │ ④c timeline.json 計算(シーン切替・字幕・強調語の絶対時刻)
      │ ⑤ WAV 連結(pacing.json の規則で無音挿入)→ narration.wav
      ▼
 timeline.json + narration.wav + assets
      │ ⑥ Remotion が timeline をフレームに変換して合成
      ▼ ⑦ 720p プレビュー ►【人間レビュー③: 見た目・テンポ】軽量
 output.mp4(約5分, 1920x1080, H.264 + AAC)
```

### 実行環境

- **MacBook Pro (M1 Pro/32GB) を主機**: 本パイプラインは VRAM 非依存。VOICEVOX は CPU で実用速度、Remotion レンダも M1 で完結。注意: VOICEVOX の Docker イメージは amd64 前提のため、Mac ではアプリ同梱エンジンを使う(Docker はエミュレーション動作になる)
- **RTX 4090 機は任意アクセラレータ**: (a) 台本生成をローカル化したい場合の Qwen2.5-32B-Int4 ホスト(24GB に収まる)、(b) 夜間バッチの高速化、(c) 将来の背景ビジュアル生成。**無くても全工程が動く**

## 3. 各工程の設計

### ① 構造パース(自動)

見出し(`## フック` `## クイズ` `## 正解` `## 解説` `## 今日から使える結論` 等)を AST として扱い、既知見出しは意味ラベルへ、未知見出し(`### ぶった斬りコーナー` 等)は `section` として素通しする寛容パーサ。`【エビデンス強度 X: ...】` は正規表現 `【エビデンス強度\s*([A-D])[:：]?\s*([^】]*)】` で構造化。クイズの選択肢・正解・出典も抽出する。

### ② シナリオ生成(自動 + プロンプト制約)

`draft.json` を Claude Code のヘッドレスモード(`claude -p`、サブスクリプション認証)に渡し、二人の会話台本 `script.json` を生成する。従量課金の API キーは使わない。

```bash
claude -p "$(cat prompts/scenario.md) 入力: $(cat build/sleep-01/draft.json)" \
       --output-format json > build/sleep-01/script.raw.json
```

API の構造化出力(JSON schema 強制)は使えないため、**生成 → スキーマ検証 → 不合格ならエラー内容を添えて再生成**の検証リトライループ(最大2回)をパイプライン側に持つ。尺・文字量の機械バリデーション(後述)と同一のゲートに統合する。

**話者**(固定2ペルソナ):
- **講師**: 要点を締める・俗説をぶった斬る役。落ち着いたトーン、`speedScale 1.0`
- **生徒**: 視聴者代表。素朴な疑問・合いの手・クイズで迷う役。軽やか、`speedScale 1.05`

**節 → 会話・映像への変換ルール**(プロンプトに明記):

| ドラフトの節 | 変換 |
|---|---|
| フック | 掛け合いのコールドオープン。生徒が「あるある」を言い、講師が「今日ぶった斬ります」 |
| クイズ | 生徒が選択肢を読み迷う。画面に選択肢を大きく表示し、2.5〜3.5秒の「考える間」。全選択肢を読み上げすぎず、音声では代表的な迷いどころだけ拾う |
| 正解 | 講師が宣言、○×アニメ |
| 解説 | 交互の掛け合い。エビデンス A の主張を山場の中心に置き、B/C は補助。重要ワードは `emphasis` にマーク |
| ぶった斬り | 最も面白い1〜2個に絞って凝縮 |
| まとめ | 「今日から使える結論」を3つ、生徒が復唱 |

**安全規範**(プロンプト制約+レビュー①チェックリストの両方に載せる):
- ドラフトにある主張以上の医療助言を足さない。ドラフトにない断定を足さない
- `【強度X】` タグは**原文からの逐語コピーを強制**(人間は改変有無だけ確認すればよい)
- 観察研究と RCT を同じ強さに見せない。「効く」「防げる」は、ドラフトが慎重に書いている場合「関連」「有望」「余地がある」に戻す
- 「飲み会」「油は無罪」など誤解を招くキャッチには、安全側の補足発話を必ず隣接させる
- 個別疾患の治療判断に見える表現は避ける

**尺・情報量の予算**(プロンプトに数値で与え、生成後に機械検証):

| 区間 | シーン数 | 秒数 |
|---|---:|---:|
| タイトル/フック | 3〜4 | 25〜35 |
| クイズ | 4〜5 | 35〜45 |
| 正解 | 2 | 15〜25 |
| 解説の山場 | 12〜16 | 150〜190 |
| 俗説訂正 | 4〜6 | 45〜60 |
| 実践結論 | 3〜4 | 35〜45 |
| 出典 | 1 | 10〜15 |

- 台本合計 1500〜1900字(日本語会話 ≈ 300〜380字/分)
- 文字量規律: 1シーンの主テキスト 28字以内、1行 14〜18字(最大22字)、補助テキスト2行まで
- 許容尺 4分40秒〜5分20秒。20分想定のフロンティア編は「約6分」に自動延長し人間に通知
- 生成後、工程③の計算尺で自動チェック → 超過なら台本圧縮を1回自動リトライ → それでも外れたらレビュー①にフラグ

### ③ 発音辞書 → audio_query(合成前・尺確定)

各 utterance を話者の style_id で `/audio_query` に投げる。専門語(インスリン感受性、山中因子、Van Dongen 等)の誤読対策として、**ドラフト横断で育てるユーザ辞書 `pronunciation.json`** を VOICEVOX のユーザ辞書 API(`POST /user_dict_word`)に反映してから照会する。未登録語は自動リストアップしてレビュー②の対象にする。

1発話の尺は合成前に次式で確定する:

```
utterance_sec =
   ( prePhonemeLength
   + Σ_moras ( (consonant_length or 0) + vowel_length )
   + Σ_accent_phrases ( pause_mora.vowel_length or 0 )
   + postPhonemeLength ) / speedScale
```

モーラを先頭から累積すれば「発話開始から t 秒後にどの文字が鳴るか」も分かり、強調語のカラオケ式ハイライトが同じデータから出せる。強調語の表層文字列→モーラ列の対応付けには漢字→カナ変換が必要(AudioQuery の `kana` を利用)。**照合に失敗したシーンは「キーワード先頭一括表示」に自動フォールバック**し、同期破綻をレンダ失敗に波及させない。

### ④ 合成・検証ゲート・timeline 生成

a. AudioQuery を `/synthesis` に渡し utterance ごとの WAV を書き出す(話者別 `speedScale` / `intonationScale`)。

b. **検証ゲート(実測照合)**: 全 WAV についてサンプル数から実測尺を取り、③の計算尺と比較する。

```python
wav, sr = sf.read(f"{utt_id}.wav")
measured = len(wav) / sr
if abs(measured - computed) > 0.05:      # 50ms 閾値
    warn(utt_id, computed, measured)
    computed = measured                   # 実測を正とする
```

エンジンのバージョン差・丸め誤差が同期に混入するのをここで遮断する。警告が頻発する場合は計算式かエンジン設定の不整合を疑うシグナルにもなる。

c. 確定した尺と語内タイミングから `timeline.json` を組み立てる(形式は §4.2)。

### ⑤ WAV 連結と「間」の挿入

utterance WAV を `pacing.json` の規則(§4.3)に従った無音を挟んで連結し `narration.wav` を作る。**無音は必ず音声ファイル側に物理挿入する**(timeline にだけ足して音声に足し忘れる、という片側更新をコードの構造として不可能にする: 連結処理が timeline への書き戻しと無音生成を同一ループで行う)。

### ⑥⑦ 映像合成(Remotion)とプレビュー

Remotion(React + TypeScript)の単一 Composition が `timeline.json` と `narration.wav` を props で受け取り、`round(sec × fps)` でフレームに変換して `<Sequence>` を配置する。`<Audio>` と同一フレームクロックを共有するため定義上ズレない。

シーン型コンポーネント(有限集合): `TitleCard` / `HookScene` / `QuizCard` / `AnswerReveal` / `ExplainScene`(強度バッジ付き)/ `MythBust`(ぶった斬り)/ `TakeawayList` / `SourceFooter`。長文は `@remotion/layout-utils` の `fitText` でオーバーフロー防止。話者表示は画面下の名前ラベル+簡易アイコンの点灯のみ(口パク・アバターは初期スコープ外)。

レビュー③用に 720p の低解像度プレビューを常設工程とする(同期が機械的に合っていても「読めるか・飽きないか」は実物を見ないと判断できない)。本番は 1080p/30fps。

```bash
npx remotion render src/index.ts HealthVideo out/sleep-01.mp4 \
    --props=./build/sleep-01/timeline.json --concurrency=8
```

## 4. 音声・映像同期の設計(本システムの核)

### 4.1 タイムスタンプの取得: 合成前計算 + 合成後実測の二重化

- **一次ソース**: AudioQuery のモーラ長累積(§3③)。合成前に決定論的に得られ、語内タイミング(強調語ハイライト)まで同じデータから出せる
- **検証**: 合成後 WAV の実測尺(§3④b)。50ms 閾値で照合し、超えたら実測採用+警告
- ASR・forced alignment は基幹ラインでは不要(クラウド TTS を使う上位ラインのみ §9 の方式)

### 4.2 同期データ形式 `timeline.json`

```json
{
  "fps": 30,
  "totalSec": 298.4,
  "audio": "narration.wav",
  "scenes": [
    {"id":"quiz","type":"quiz","startSec":41.2,"endSec":63.8,
     "onScreen":{"question":"…","options":["A …","B …"]},
     "utterances":[
       {"speaker":"student","startSec":41.2,"endSec":45.0,
        "wordTimings":[{"text":"全部","startSec":41.5,"endSec":41.9}]},
       {"speaker":"teacher","startSec":45.3,"endSec":48.1,
        "emphasis":[{"text":"止めて","startSec":46.0,"endSec":46.5}]}
     ]}
  ]
}
```

この形式は**TTS バックエンドとの契約**である。上位ライン(§9)や将来の差し替えは、この形式さえ生成すれば後段(Remotion・レビュー体系・レンダ)を一切変えずに載る。

### 4.3 会話の「間」の規則(`pacing.json`)

| 状況 | 挿入無音 |
|---|---|
| 同一話者の文継続 | 120–180 ms |
| 話者交代(通常) | 250–350 ms |
| ツッコミの後 | 180–280 ms |
| クイズ選択肢間 | 180–260 ms |
| 問い→答え・正解発表前 | 450–650 ms(一拍おく) |
| 重要結論の後 | 400–600 ms |
| シーン境界(話題転換) | 600–800 ms |
| クイズの「考える間」 | 2.5–3.5 s(画面は選択肢のまま、BGM のみ) |

定数は `pacing.json` に切り出し、レビュー③で微調整可能。utterance 個別の指定(`pause_after_ms`)があればそちらを優先する。

### 4.4 尺の揺れへの対処(長すぎ/短すぎの両側)

- **長すぎる場合**(自動、この順で): (1) pause を安全範囲内で圧縮 → (2) シーンの余白アニメーション短縮 → (3) LLM に「削除可能発話」だけ再圧縮させる → (4) それでも 5分20秒超ならレビュー①で人間が削る
- **短すぎる場合**: 無音を増やして水増ししない。フックや実践結論の発話を少し厚くする(教育動画としての理解時間を守るため)

## 5. 人間の関与ポイント(3レビュー)

自動化が信頼できる工程(尺計算・照合・連結・フレーム割当・レンダ・バッチ)は人手を入れない。品質リスクが高く自動判定が難しい3点のみ:

### レビュー① 台本(必須・最重要)
- **対象**: `script.json`(Markdown プレビュー+原文対応表示)
- **見るもの**: 医学的主張・数値・エビデンス強度が原文を歪めていないか(`【強度X】` は逐語コピーなので改変有無の確認のみ)/ §3② の安全規範チェックリスト / 俗説の否定が肯定にすり替わっていないか / 軽妙なトーンが「ふざけすぎ」になっていないか / 5分の山場が1〜2個に絞れているか
- **なぜ**: 健康情報は誤りが害になる。LLM は強度 A の断定と強度 C の示唆を混ぜうる。唯一にして最大の品質ゲート
- **直し方**: JSON を直接編集 → 承認で工程③起動

### レビュー② 読み・アクセント(軽量・スポット)
- **対象**: 「辞書未登録語」として自動リストアップされた語の WAV のみ
- **インターフェース**: WAV 再生+該当行表示+辞書登録ボタンだけの 30 行程度のローカル HTML(初期構築で作る)
- **なぜ**: 誤読は文字列一致で検出できず耳が要る。辞書 `pronunciation.json` に一度直せば10本で再利用され、回を追うごとに手間が減る

### レビュー③ 見た目・テンポ(軽量)
- **対象**: 720p プレビュー+Remotion Studio のスクラブ
- **見るもの**: 文字の被り・選択肢の可読性・切替の先走り・間の気持ちよさ・飽きる区間
- **直し方**: `pacing.json` の定数、`emphasis` 語の増減、headline の短縮。コンポーネントは触らない

## 6. コンテンツ品質の設計

- **巨大強調語**: `ExplainScene` は画面中央に巨大な強調語1つ(例:「督促状が来なくなる借金」)+下に一行補足を基本形に。カラオケ式ハイライトで今喋っている語が光る
- **皮肉・比喩は殺さない**: 「救急車を廃車にする」等は講師のセリフとして残し、画面に短い図解 or 大文字で添える
- **クイズの体験化**: 選択肢カード表示 → 生徒が声で迷う → 考える間 2.5〜3.5秒 → ○×アニメ
- **エビデンス強度の可視化**: 強度A=緑 / B=黄 / C・D=グレーのバッジ。「観察研究(因果は保留)」等のニュアンスを色と短語で伝え、画面から消さない
- **1シーン=1メッセージ**: 平均10〜18秒/シーン、全体 20〜30 シーン(§3② の予算表)
- **統一トーン**: ダークテーマ(リポジトリ慣習に整合)、Noto Sans JP バンドル+`<Font>` 明示ロード、トピックごとにアクセント色1つ。10本でブランドが揃う

## 8. リスクと対策

| リスク | 対策 |
|---|---|
| LLM が事実・強度を歪める、断定を強める | 安全規範のプロンプト制約+逐語コピー強制+レビュー①必須+原文対応表示 |
| 計算尺とエンジン実挙動の乖離 | ④b 実測検証ゲート(50ms 閾値、実測優先+警告) |
| 専門語の誤読 | 横断辞書 `pronunciation.json` + 未登録語の自動リストアップでレビュー②を最小化 |
| 音声と timeline の片側更新ずれ | 無音挿入と timeline 書き戻しを同一ループで実装(構造的に分離不可能にする) |
| 合成音声の単調さ | 話者別 speed/intonation、pacing 規則、BGM ベッド。不足する回は上位ライン(§9)へ |
| 尺の逸脱 | 合成前尺チェック → 自動圧縮リトライ → 人間フラグ。短すぎは内容を厚くする(§4.4) |
| 強調語のモーラ照合ミス | 先頭一括表示へ自動フォールバック |
| ドラフト形式の揺れ | 寛容パーサ+シーン予算の動的調整+未知セクションは補助素材扱い |
| 文字オーバーフロー | 文字量規律の生成時バリデーション+`fitText`+レビュー③ |
| Remotion/フォントのライセンス | Noto Sans JP バンドル。利用規模に応じ Remotion ライセンス確認 |

## 9. 上位ライン(看板回向け): Azure WordBoundary 経路

声の自然さ・感情が視聴体験の決め手になる回(例: `お金で幸福は買えるか`)向けのオプション。基幹の `timeline.json` 契約(§4.2)に別ソースから流し込むだけで、後段は無改変。

- **TTS**: Azure AI Speech(日本語 Neural・複数話者・SSML で間と抑揚を制御)
- **同期**: 合成と同時に返る `WordBoundary` イベント(`AudioOffset`、100ns 単位→秒)を `wordTimings` に変換。後付け ASR 不要。フォールバックは whisper.cpp `--dtw` の強制アライメント(ローカル・4090 で高速)
- **尺揺れ**: 事前確定不可のため、合成→実測→5分ガード判定→超過なら台本圧縮して再合成。**再合成は最大2回**でコスト上限を切り、それでも超過は人間レビューへ
- **コスト**: Azure Neural TTS は**約 $16/100万文字**。台本 ~3600字/本 → 約 $0.06 ≒ **¥9/本**(微少。ただしコンテスト時の $4/百万字は誤りだったので注意)
- **コンプライアンス**: 外部送信は台本のみ(原ドラフトは送らない)。懸念があればアライメントをローカルに留める
- **混在可**: 回ごと・話者ごとに TTS を混在できる(例: 講師=VOICEVOX、生徒=Azure)

導入は基幹ラインが2本目検証を通ってから。差分実装 +0.5〜1人日。

## 11. 再現性・拡張性

- ドラフト固有情報はすべてデータ側(`draft.md` → `script.json` → `timeline.json`)。コードは10本共通で、新ドラフトは「差し替えて render」するだけ
- **育つ資産**: `pronunciation.json`(読み辞書)、`pacing.json`(間)、デザイントークン、プロンプト。回を重ねるほど手間が逓減
- 声の変更 = style_id 差し替えのみ。テンプレ追加 = シーン型コンポーネント1つ。TTS 差し替え = `timeline.json` 契約で後段無改変
- 縦型ショート版・字幕焼き込みは Remotion の別 Composition を足せば同一データから派生可能

## 12. 拡張ロードマップ(Phase 2 以降)

いずれも基幹ラインが2本目の無改造検証(§10 Step 6)を通ってから導入する。データ契約(script.json / timeline.json)には受け皿フィールドを先に定義してよいが、実装は持ち込まない。

### 12.1 比喩イラストのローカル生成(RTX 4090)

情報を運ぶ図(グラフ・仕組み図・バッジ)は今後もコード描画(SVG)を維持する。生成イラストの対象は**装飾的な比喩挿絵のみ**(例:「督促状が来なくなる借金」「救急車を廃車にする」)。細部の捏造が実害にならない箇所に限定する。

- **フロー**: シナリオ生成時に LLM が対象シーン(`analogy` 系レイアウトのみ)へ `illustration_prompt` を出力 → RTX 4090 の SDXL/FLUX でローカル生成(1枚10〜20秒・¥0)→ **レビュー①で台本と同時に採用可否を判断** → 採用分のみ assets に配置し、Remotion が `<Img>` で表示
- **絵柄の一貫性**: スタイルプリセット(固定スタイルプロンプト、必要なら LoRA)で全10本のタッチを統一。シリーズの信頼感を損なう絵柄ドリフトを防ぐ
- **不採用時の既定動作**: 生成イラストがなくてもシーンは巨大タイポグラフィ+SVG アイコンで成立する(イラストは常に「あれば足す」装飾であり、必須依存にしない)
- **レビュー負荷の上限**: 1本あたり生成対象は2〜4シーンまで。人間30〜60分/本の予算を崩さない

### 12.2 アニメーションプリセット方式(演出の語彙化)

演出の**選択**はデータ(LLM)、演出の**実装**はテンプレートに分離し、アニメーションを「育つ語彙」として増やす。

- script.json のシーンに `animation` フィールドを追加し、LLM が有限集合から選ぶ:

```json
{ "headline": "認知成績は14日間、下がり続けた",
  "animation": "count_down_graph",
  "emphasis": ["下がり続けた"] }
```

- Remotion 側はプリセット名 → 実装のマッピングを1箇所に持つ。未知・未指定の名前は既定演出(フェードイン)へフォールバックし、破綻させない
- **初期語彙(案)**: `pop`(強調語がドンと出る)/ `count_up`(数字カウントアップ)/ `strike_through`(俗説に赤線=ぶった斬り)/ `stack_up`(積み上がるメタファー)/ `bar_race`(棒グラフが伸びる)
- **語彙の増やし方**: 新プリセットを1つ書く(React/CSS/SVG、数十分〜数時間)→ プロンプトの選択肢一覧に追記 → 以降すべての動画で LLM が選べる。**特定の動画専用のアニメコードは書かない**(再現性の維持)
- **口パク(将来)**: timeline.json には既にモーラ単位の母音タイミングが入っているため、導入時もデータ追加は不要。プリセット実装のみで足せる

### 12.3 リッチアニメーション(必要になった場合のみ)

デザイナー品質の動きが必要になったら、After Effects 製アニメを Lottie 書き出しして `@remotion/lottie` で再生する経路を使う。プリセット方式(12.2)と同じマッピングに載せられるため、アーキテクチャ変更は不要。
